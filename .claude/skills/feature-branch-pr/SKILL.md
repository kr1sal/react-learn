# feature-branch-pr

Скилл для работы над любой новой фичей или мини-проектом в этом репозитории. Задача — не коммитить прямо в основную ветку, а завести отдельную ветку, сделать коммиты и открыть pull request, придерживаясь стиля, уже принятого в репозитории.

## Когда применять

- Пользователь просит начать новую фичу, эксперимент, мини-проект, задачу или багфикс.
- Пользователь говорит «сделай ветку», «оформи PR», «заведи pull request» и т. п.
- Перед крупным изменением, которое не должно ехать напрямую в основную ветку.

Если правки тривиальны и пользователь явно попросил «просто закоммить в main» — скилл не применять.

## Порядок действий

### 1. Проверить состояние репозитория

```powershell
git rev-parse --is-inside-work-tree
git status
git remote -v
git branch --show-current
git log --oneline -1
```

- Если это не git-репозиторий — спросить пользователя, инициализировать ли (`git init`), не делать это молча.
- Если есть незакоммиченные изменения на текущей ветке — прежде чем переключаться, `git stash -u` или уточнить у пользователя.
- Определить имя основной ветки: `git symbolic-ref refs/remotes/origin/HEAD` → `refs/remotes/origin/<main|master>`. Если remote нет — использовать `main`, если она есть локально, иначе текущую.

### 2. Изучить стиль репозитория

Прежде чем именовать ветку или писать сообщения, посмотреть, как это делали раньше:

```powershell
git log --pretty=format:"%s" -30
git log --pretty=format:"%s%n%n%b%n---" -10
git branch -a
git log --all --pretty=format:"%D" -50
```

Определить:

- **Стиль коммитов**: Conventional Commits (`feat:`, `fix:`, `chore:`…), просто императив на английском, русский язык, эмодзи, префиксы вида `[TASK-123]` и т. п.
- **Схему именования веток**: `feature/<slug>`, `feat/<slug>`, `<username>/<slug>`, `task-123-<slug>` и т. п. Разделители (`-` vs `_`), язык слага (обычно английский kebab-case, даже если коммиты на русском).
- **Язык описаний PR**: посмотреть последние merge-коммиты (`git log --merges --pretty=format:"%s%n%n%b%n---" -5`) и, если есть `gh`, `gh pr list --state all --limit 10` и `gh pr view <n>`.

Если история пустая (нет коммитов) — использовать разумные дефолты:

- Ветка: `feature/<kebab-slug>`
- Коммиты: Conventional Commits на языке первого запроса пользователя.
- PR: секции `## Summary` и `## Test plan`.

### 3. Создать ветку

```powershell
git checkout <main-branch>
git pull --ff-only    # только если есть remote и ветка его отслеживает
git checkout -b <prefix>/<slug>
```

Слаг — короткое английское kebab-case описание фичи (3–5 слов максимум). Если пользователь дал русское название — транслитерировать/перевести в короткий английский слаг, если только в истории репозитория ветки не именуются иначе.

### 4. Делать коммиты по ходу работы

- Коммитить логическими порциями, а не одной свалкой в конце.
- Сообщения — в стиле репозитория (см. шаг 2).
- Только те файлы, что относятся к фиче: `git add <конкретные пути>`, избегать `git add -A`, если в рабочей копии есть посторонние файлы.
- Перед `git add` быстро глянуть `git status`; если попал подозрительный файл (`.env`, `*.pem`, что-то с ключами) — не коммитить, спросить.
- В конце сообщения коммита добавлять trailer’ы:

```
Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com>
Claude-Session: https://claude.ai/code/session_01AhkEGfnRm4KXttrcEA5VP2
```

Передавать сообщение через heredoc/here-string, чтобы не поломать форматирование.

### 5. Открыть Pull Request

Если настроен `gh` и есть remote:

```powershell
git push -u origin <branch>
gh pr create --base <main-branch> --title "<заголовок>" --body @'
## Summary
- <1–3 буллета: что и зачем>

## Test plan
- [ ] <как проверить>

🤖 Generated with [Claude Code](https://claude.com/claude-code)

https://claude.ai/code/session_01AhkEGfnRm4KXttrcEA5VP2
'@
```

- Заголовок PR — до 70 символов, в стиле, увиденном в истории (часто = сообщение первого/единственного коммита).
- Язык описания — как в существующих PR; если PR ещё не было, использовать язык, на котором общается пользователь.
- Секции подстраивать под то, что видно в старых PR (у некоторых команд принят `## Context`, `## Changes`, `## Screenshots` и т. п.).

Если `gh` не установлен или remote отсутствует:

- Сделать `git push -u origin <branch>` (при наличии remote) и отдать пользователю URL для создания PR (обычно GitHub печатает его в stderr push’а).
- Если remote нет — сообщить пользователю: ветка создана локально, для PR нужен remote; предложить его добавить, но не делать это самому.

### 6. Отчитаться пользователю

Коротко: имя ветки, список коммитов (`git log <main>..HEAD --oneline`), ссылка на PR (если создан).

## Чего избегать

- Не коммитить и не пушить в основную ветку напрямую.
- Не использовать `--force`, `--no-verify`, `--amend` для уже запушенных коммитов без явной просьбы.
- Не делать `git add -A` вслепую.
- Не выдумывать стиль — если в истории уже есть свой, следовать ему, даже если он необычный.
- Не переводить сообщения на другой язык, если в репозитории все коммиты на одном конкретном языке.
